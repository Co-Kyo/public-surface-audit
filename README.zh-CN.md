# public-surface-audit

[English](README.md) · **中文**

> **让陌生读者先读过，再发布。** 本程序审的**公开面**，是团队以外的人能读到的每一个字——它把这些字交给第一次见到它们的读者逐条审，按批次出 PASS/FAIL。没过的那一批，不发布。

Agent Skill · 两种模式 · 四步程序 · 11 条红线 · MIT

## 问题出在哪

一份 README 你读过几十遍——问题恰恰在这里。每句话为什么这么写，你知道；读者不知道。写作现场本身就是污染源，这是你站在里面审不出来的那件事。

所以要问的不是**"这句写得好不好"**，而是**"这句话该不该给陌生人读"**。绝大多数泄漏不是文笔差，而是写给了"自己人"看的东西：一条决策记录、一轮检查经过、一个工单号、一张修复账。在门里都正常，出了门就是事故。

词表脚本也回答不了这个问题：它看得见词的形状，看不见语气，看不见一句话根本不该存在，也看不见一句承诺背后有没有东西。判据总共一句话，写在 [`references/charter.md`](references/charter.md) 里：**这句话是帮读者用好的，还是帮自己记事的？后者一律不要发布。** 拿到任何文件先做的是弃留判断——这条信息到底该不该出现在公开面。

读者只带三个问题来：**用不用**得着、**怎么用**、**信到哪**。一句话改变不了其中任何一个判断，就是读者替你付的重量。

## 这不是什么

本节本身就是宪章翻译规则里五种成品之一——**边界声明**，回答"信到哪"。写法也按它要求的方式：每条一句，不展开论证。

| 不是这个 | 边界划在哪 |
|---|---|
| 不是文案润色、SEO、翻译 | 它不把句子改漂亮，也不争排名。它判的是这句话该不该出现在陌生人眼前。 |
| 不是词表扫描器 | [`scripts/redline-check.mjs`](scripts/redline-check.mjs) 是召回工具，不是门。**脚本清零 ≠ 可发布**——语气、弃留、红线 10 与 11，正则一概看不见。 |
| 不读你的源码替你验实现 | 它标出无据宣称并路由回去。队列会*定位*实现、把声称的量与实际的量并列，但**不下判断**——把每句承诺对上源码签名，仍是裁决步里你自己做的活。它不替你做判断。 |
| 不承诺内容写得好不好 | 写得好不好归写作层，不属于工具承诺。把两者混说正是红线 9——本程序不做它自己审的那件事。 |

## 怎么跑

四步。绝大部分工作就在你已经在的这个会话里完成——图做机械配对，你做判断，最后一个陌生读者补上你看不见的那一块。

| 步 | 干什么 | 谁做 | 产物 |
|---|---|---|---|
| 00 | **定标**：圈文件集、切批次、给每批标性质门 | 你 | 批次清单 |
| 01 | **取证**：**先只读文本**记下它声称了什么，再逐条对实现核量 | 你 | 证据单 |
| 02 | **裁决**：逐条打开原文核对，出 PASS/FAIL | 你 | 裁决表 |
| 03 | **对抗复查与收口**：一个陌生读者冷读一遍，然后路由、给门凭据 | 复查者＋你 | 复查记录＋收口记录 |

撑起这套程序的只有三条规矩：

- **先文本后代码。** 在打开实现之前，先记下这句话声称了什么。`claims.json` 的写入早于任何 `queue` 输出，所以顺序可查——从实现出发去抽声称，抽出来的已经知道答案了。
- **批次不重叠。** 一个文件只归一批。否则同一句话被两套判据同时过，而漏检就藏在两批之间的缝里。
- **一个陌生读者，只一次，在收口前。** 不是每批一个。它只拿到文本和宪章——没有裁决表、没有源码、没有图。它不判违规，只报告"第一次读到这里我的反应是什么"，怎么处置由你定。

各步细则见 [`references/procedure/00-scope.md`](references/procedure/00-scope.md) 至 [`references/procedure/03-close.md`](references/procedure/03-close.md)。

## 抓什么

11 条红线。看右列，数数你自己文档里中了几条。

| # | 红线 | 会踩中的句子 |
|---|---|---|
| 1 | 内部档案格式——对外文字写成了工作记录 | `裁定：…｜依据：…｜触发条件：…` |
| 2 | 内部过程史——轮次、检查、来龙去脉，读者一次都没参与过 | `经过三轮复核，验收门全绿` |
| 3 | 内部编号与黑话——只有团队认得的代号 | `fix #4821，第三轮返工` |
| 4 | 缺陷自曝与修复台账——把自己的问题清单摆给读者 | `问题×归因×处置`表 |
| 5 | 设计哲学布道——向读者宣讲内部怎么想质量 | `先区分两种质量，因为……` |
| 6 | 未兑现承诺与路线图泄漏——将来时 | `v0.5 将支持增量构建` |
| 7 | 内部锚点——出门就查不到的指路信息 | `见 commit 9f2c1ab` |
| 8 | 自我贬抑式诚实——交代自己曾经多糟 | `这段一度是坏的，全部认账` |
| 9 | 质量混谈——把内容质量说成工具承诺 | `保证文档写得专业` |
| 10 | 无据行为宣称——"会 X"背后没有测试或构建期检查 | `能对任何目录运行`，而没有任何东西测它 |
| 11 | 推责式划界——把边界说成"那是你的事" | `写得好不好，取决于你的评审流程` |

第 10、11 条机器查不出，只能逐句对账。第 1–9 条在召回脚本里各有一条以上正则兜底，宁误报不漏报；误报行加一句尾注放行即可。

## 安装

不需要构建。脚本是单个 Node 文件，零依赖（Node ≥ 18）。

Claude Code 或任何兼容 harness：

```bash
# 个人 skills 目录，所有项目可用
git clone <repo-url> ~/.claude/skills/public-surface-audit

# 或只给当前项目，跟着仓库走
git clone <repo-url> .claude/skills/public-surface-audit
```

手动：把目录放进你的 harness 所读的 skills 目录。

```bash
cp -r public-surface-audit ~/.claude/skills/
```

每个仓装一次：`node scripts/graph-audit.mjs init --root .` 建出 `.audit/`、把 `.audit/` 与 `graphify-out/` 写进 `.gitignore`，并打印建图命令。然后建一次图：

```bash
export GRAPHIFY_OUT=$PWD/.audit/graphify-out   # 必须——原因见下文"建立在 graphify 之上"
graphify update                                 # 首建与以后每轮的增量都是这条，不需要 API key
```

此后跑一轮审计就是几条命令——见下文"建立在 graphify 之上"。

**语言边界：** 参考件为中文，技术词保留英文（PASS/FAIL、diff、CLI、批次号、`file:line`）。本页是中文入口，判断体在宪章里。

## 快速开始

自然语言直接说，模式它会自己认。

**发版本前的增量门**

> 按这次要发的范围跑一次公开面审计：diff 里的全部文件，加上每次发布都会重新公开的那些——README、包页描述、CHANGELOG。

预期 `.audit/rounds/{date}-{slug}/` 会逐渐填满：批次清单、每批一份证据单、一张裁决表、一份复查记录，以及一句门凭据或一份待处理的 FAIL 清单。

**开源前的存量全扫**

> 这个仓要开源，把公开面整体扫一遍——五条通道全扫，提交历史和 PR 标题也算。

预期产物：按通道分批的清单，每批一个独立 PASS/FAIL。不会有"共 N 处问题、整体良好"这种总结句——跨通道聚合数字是明令禁止的。

**单篇 README 快审**

> 这份 README 能发吗？

预期产物：一个批次、一张带 `file:line` 的裁决表、一个 PASS/FAIL，以及要改的那几行原句。

## 产物长什么样

每次跑一个目录，跑完可归档，也可直接删：

```
.audit/rounds/{date}-{slug}/
├── STATE.md            跑到哪了：已完成步骤、各批状态
├── 00-scope.md         文件集、批次划分、每批的性质门
├── 01-evidence-B1.md   B1 的证据单：先记它声称什么，再记量对上了没有
├── 02-verdict.md       逐条 PASS/FAIL，每条带原文 file:line
├── 03-review.md        陌生读者读到了什么，以及你怎么处置
└── 03-close.md         每条发现去了哪，以及门凭据
```

门凭据只有一句话，写在全部批次 PASS 之后，并且必须能指回裁决表里的逐条证据。指不回去，就不算凭据。

## 建立在 graphify 之上（强制依赖）

本 skill 站在 **graphify** skill 的知识图之上——这是硬依赖，不是可选插件。判断仍是人的；检索、配对、记忆一律走图，而图就住在被审仓里。

**审计工作区属于对象。** `node scripts/graph-audit.mjs init --root <仓>` 在项目根目录建 `.audit/` 并自动写进 `.gitignore`——审计的过程文件不进版本库、不进公开面。三层共用一张图：

| 层 | 是什么 | 谁写 |
|---|---|---|
| 图基座 | 文件、符号、社区 | graphify skill（build／update） |
| 声称层 | claim 节点 ＋ claim→符号 配对边 | `graph-audit ingest-claims` |
| 裁决层 | claim 节点上的 `audit_verdict` 等属性 | `graph-audit record` |

**记忆就是图本身。** 文件内容哈希没变的声称下轮不再入队；改过的重新入队并带上上轮裁决。**判断跟着内容走，不跟着时间走。** `graphify update` 会保留审计层（实测），但**源文件被删掉时**，挂在它上面的 claim 节点会被连带驱逐——文件增删之后跑一次 `graph-audit reconcile` 把记忆补回来。

**一个环境变量撑着整条图链。** `graphify update` 不接受 `--out`，它写到「目标目录上一级的 `graphify-out/`」。在 `.audit` 里跑它就落到仓根，而脚本读 `.audit/graphify-out/`——从此增量静默失效。设 `GRAPHIFY_OUT=<仓>/.audit/graphify-out`（绝对路径，与当前目录无关），`extract` 与 `update` 才在同一条链上。仓根另有一张图时 `graph-audit status` 会报警。

**没有 API key 不是死路。** `graphify extract .` 处理文档需要 LLM key，`graphify update` 不需要——它产出代码符号加上文档的结构节点（page／heading），够跑队列。**不要退回 `--code-only`**：它的文档节点是 0，配对已失效，却和正常图长得一样。

**大部分违规根本不用核代码。** 标为 `future`／`process`／`quality` 的声称（未来时、开发过程史、自我夸赞）本身就是违规——分别是红线 6、2、9，直接进裁决表。

**符号找不到本身就是发现。** 图与源码里都没有 `verify`，说明文档描述了一个不存在的东西——这是置信度最高的信号。**配对靠符号，不靠词**：`check`、`push` 这类词到处都是，靠词面匹配只会淹没在误报里。

**队列不下判断。** 它只把"文档说会怎样"与"函数体实际怎样"并列；对不上也可能是你读错，每条仍须对原文确认。**它给的是"哪段文字关于这个主题"，不是"这句话违不违规"**——拿它问一个语气问题，它会返回几十个相关节点，一个都不回答问题。队列为空也不等于公开面干净——"我们保证写得专业"在代码里根本没有对应物。架构与实测陷阱见 [`references/graphify-integration.md`](references/graphify-integration.md)。

## 自检

本仓先在自身上跑这套程序：

- [`self-check.yml`](.github/workflows/self-check.yml) 每次 push 和 PR 都在仓库自身上跑 `node scripts/redline-check.mjs --stat .`。
- [`examples/before-after/`](examples/before-after/) 是真实改写，每组标注违反了哪条红线。
- [`examples/walkthrough/`](examples/walkthrough/) 记录一次完整实录，从定标一直跑到收口。这一轮里词表召回零命中，裁决仍成立 5 条——"门是审计不是脚本"在这份实录里是跑出来的，不是说的。
- 同一份实录结尾，是这套程序审**它自己的 `SKILL.md`**。陌生读者提了 8 条，8 条全部成立，其中 6 条是其他各层一条都抓不到的：一个代词指了两个人、一个术语在定义之前先用了、一条规则自己跟自己矛盾、一段论证前后两半互相抵消。最后那条正是这一步存在的理由——它找出了作者读了三遍都没发现的裂缝。

这个程序先过自己的门，再来要求你过你的门。
