# claim-extraction-spec：把"对外声称"抽成可核验节点

> 这是本 skill 交给**声称抽取 agent**（只读文档、不看代码的新上下文）的定制抽取规格。
> 产出经 `graph-audit.mjs ingest-claims` 成为图上的 claim 节点与配对边（见 `graphify-integration.md`）。
> 目标不是"理解文档"，而是产出**能与实现精确配对**的节点：每条声称必须带 `targets`（它在说哪个符号），否则配对只能靠猜词，而猜词在真语料上不可用（见文末实测）。

## 为什么需要定制规格

graphify 默认规格抽的是"概念与主题"——适合理解与导航，不适合审计。审计要的是另一种东西：

- 默认抽出的 `退出码 2 表示名单不一致` 是一个概念节点，**没有说它属于哪个函数**，于是只能拿"2"和"退出码"去全文撞词，撞出一堆噪声；
- 定制规格要求它回答"这句话在约定**哪个符号**的行为"，产出 `targets: ["shipAssets check"]`——于是配对变成符号定位，精确到函数，噪声归零。

**一句话**：默认规格服务于"读懂"，本规格服务于"核对"。

## 抽取目标

读给定文件，抽出其中**可被证伪的事实性声称**，每条声称成为一个节点。

只抽可能被证明为假或与实现不符的句子。以下**不要**抽：

- 纯背景介绍、愿景、形容词堆叠（"轻量、快速、优雅"）；
- 纯操作步骤（"运行 npm install"）——除非它附带可核验的行为断言；
- 内部激励语、寒暄、目录、链接列表。

## 每个节点的字段

```json
{
  "id": "readme_check_exit_code",
  "label": "一句话复述这条声称，必须保留原文全部具体量",
  "file_type": "concept",
  "source_file": "<文件路径，逐字照抄 FILE_LIST 里的写法>",
  "source_location": "L<行号>",
  "confidence": "EXTRACTED | INFERRED",
  "claim_kind": "behavior | boundary | version | future | process | quality | reference",
  "targets": ["<这条声称在约定哪个符号/命令/字段的行为>"],
  "quantities": ["<声称里出现的可核验量>"]
}
```

### `claim_kind` 取值（七类，判定互斥）

| 值 | 含义 | 例子 | 谁能核 |
|---|---|---|---|
| `behavior` | 说某工具/命令**会**做什么 | "任一项对不上就以退出码 2 结束" | 代码——符号定位到函数，查实现 |
| `boundary` | 说它**不会**做什么 | "不比对文件内容" | 代码——同上，查有无该能力 |
| `version` | 与具体版本号绑定的行为 | "0.3.0 起接进构建" | CHANGELOG / git 历史 |
| `future` | 未来时：会支持、计划中、排在后面 | "0.5 会比对文件内容（哈希）" | 无需核实现——**它本身就是红线 6** |
| `process` | 讲开发过程、轮次、返工、修复史 | "中间返工了两轮" | 无需核实现——**本身就是红线 2** |
| `quality` | 对质量/优劣的自我评价 | "保证产物专业" | 无人能核——**本身就是红线 9** |
| `reference` | 指向另一个文件/命令/链接 | "完整写法见 docs/guide/publish.md" | 文件是否存在、章节是否真有（**悬空引用**） |

**其中三类是"抽出来就是结论"的**：`future`／`process`／`quality` 一旦被抽出，不需要进入配对环节——它们按宪章就是违规候选，直接进发现清单。这是本规格最大的效率来源：**大部分违规根本不用核代码。**

### `targets` 怎么填（最关键的一栏）

写**符号名**——代码里真实存在或声称存在的那个东西，不是描述性短语：

- ✅ `"shipAssets check"`、`"check()"`、`"package.json 的 files 字段"`、`"--dry-run"`
- ❌ `"检查逻辑"`、`"配置部分"`、`"主流程"`（无法定位，等于没填）

规则：

1. 一句话只约定一个符号 → `targets` 一项；一句话涉及多个 → 全列。
2. 命令写成 `<命令> <子命令>`（`shipAssets check`），函数写成 `name()`。
3. **无法确定目标符号时填 `[]` 并在 label 里保留原句**——不要编一个看起来像符号的词。空 targets 的节点仍会进人工队列。
4. 目标是本仓之外的（第三方库、平台行为）写成 `"external:<名字>"`，配对环节会跳过。

### `quantities` 怎么填

把声称里所有可核验的量抄进来，用于与实现里的量对照：

- 退出码、阈值、条数、版本号、默认值、字段名、路径、文件扩展名。
- 例：「任一项对不上就以退出码 2 结束」→ `["退出码 2", "任一项"]`
- 例：「只支持 .md 和 .mdx」→ `[".md", ".mdx"]`

**量的作用是发现"方向对但细节错"**——这是审计里最难靠人眼发现的一类（文档说 2，实现里缺文件走 2、越界走 1）。

## 输出格式与去向

```json
{
  "nodes": [ ...按上面字段... ],
  "coverage": { "<每个读到的文件>": <读到的行数> }
}
```

`coverage` 必须如实填——它是"这份文件我真读完了"的唯一凭据，抽取流程会拿它和文件真实行数比对。

产出的这份 JSON 交给 `node scripts/graph-audit.mjs ingest-claims --root <被审仓> --in <本文件>`：每条声称成为图上的 **claim 节点**（`_origin: "audit-overlay"`，带 `claim_kind`／`targets`／`quantities` 属性），`targets` 命中的符号自动生成 **claim→符号 配对边**（`relation: "references"`）。此后检索、排队、记裁决全走图——见 `graphify-integration.md`。

## 边界情况判定

| 情况 | 怎么做 |
|---|---|
| 同一件事在两个文件里说法不一致 | **各抽一个节点**，不要合并、不要择一。不一致本身是最有价值的发现 |
| 一句话既讲行为又讲排期 | **拆成两个节点**（`behavior` + `future`），因为一个要核代码、一个直接违规。同一 `source_location` 允许出现多个节点 |
| 拆不动（半句边界＋半句排期，如"目前只比对文件名，0.5 会比对内容"） | 加 `claim_kind_secondary` 字段：`{"claim_kind":"future","claim_kind_secondary":"boundary"}`。**主 kind 决定处置路径，次要 kind 也要核**——不然可核的那半句会漏掉 |
| 表格里的一行 | 照抽，`source_location` 指到那一行 |
| 代码块里的注释 | 抽——源码注释会第二次公开（见宪章通道四） |
| 同一句在文件里重复出现 | 抽一次，`source_location` 指首次出现 |
| 全是边界声明、没有行为声明的文件 | 全部按 `boundary` 抽，这是正常的，不要求凑数 |

## 自检（提交前逐条过）

1. 每条 `label` 里的量，在 `quantities` 里都有对应？漏了就是"没法核的声称"。
2. 每条 `behavior`/`boundary` 的 `targets` 非空，且写的是符号名不是描述？
3. `future`/`process`/`quality` 有没有被错标成 `behavior`？（错标会让它进代码核对，白跑一轮）
4. `coverage` 的行数是否等于文件真实行数？（只读了前 100 行就填 100，别填总数）

## 实测记录（为什么这份规格存在）

**默认规格 + 词频配对，在真语料上不可用**：在一个约 41 文件的仓库上跑词频配对，队列排出 3 条，**全部误报**（`redline`、`audit`、`queue` 这类词在代码里到处都是，一句声称撞出 20 多处）。

**定制规格 + 符号配对，同样的语料上精确命中**：

| 声称 | targets | 定位结果 | 判定 |
|---|---|---|---|
| 任一项对不上就以退出码 2 结束 | `shipAssets check` | `check()` @ L9 | 函数体内 `exit(1)`、`exit(2)`、`exit(0)` 并存 → **驳倒**（方向对、细节错） |
| check 只核对，不写盘 | `shipAssets check` | `check()` @ L9 | 体内无写盘调用 → 证实 |
| shipAssets verify 构建后核对… | `shipAssets verify` | **0 处** | 该命令在源码中不存在 → **无定／驳倒**（最高置信度信号） |

最后一行值得单独说：**"符号找不到"本身就是结论**。词频法很难得出这个结论——"verify"这个词在别处出现反而会稀释信号；符号定位把它变成一条硬事实：文档描述了一个不存在的命令。

## 与主程序的关系

- 本规格只服务于**步骤 03 回捕网**（承诺句对签名），不替代审计者的判断。
- `future`／`process`／`quality` 抽出来即违规候选（红线 6／2／9），不用进配对；`behavior`／`boundary`／`version` 进配对队列。
- 配对即图查询：claim 节点按 `targets` 里的符号名生成 claim→符号边；**符号在图与源码里都找不到 = 高置信信号**（文档描述了不存在的东西）。
- **配对结果一律不自动定案**：量对不上也可能是主持者读错（同名函数、分支差异），须主持者逐条打开原文确认——遵守 `procedure/03-adjudicate.md` 第 1 条（不做转述式验收）。
