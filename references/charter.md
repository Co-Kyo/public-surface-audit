# 公开面宪章 · 什么算违规

> 本件回答"什么算违规"；执行程序（谁来查、怎么查、查完东西放哪）见 `procedure/`。
> 判据一句话：**这句话是帮读者用好的，还是帮自己记事的？后者一律不要发布。**

## 定名与分界

**公开面**＝团队以外的人能读到的每一个字。

**归属判据**（任何文件拿到手先问这一句）：这份文字会被团队以外的人读到吗？会 → 归本宪章管；不会 → 不归它管。

两个容易混的边界：

- **本仓库自己是公开面。**本 skill 的每个字都会被人读到，所以它必须过自己的审计——这不是比喻。`examples/walkthrough/` 是一次完整的四步实录（审的对象是一个虚构小包），本仓自身的审计记录在 `.audit/rounds/` 里。任何"我自己的检查工具不必遵守自己的规则"的例外，都是漏检的口子。
- **和"内容真假"怎么分工。**同一句话要过两道不同的检查：本宪章问**这句话该不该给陌生人读**（用词、口吻、有没有把内部的事抖出去）；"这句话是不是真的、有没有测试撑得住"是另一道检查（红线 10 是它的入口）。两道都要过，各管一头。

## 读者 · 目的 · 口吻

- **读者**：团队以外的人。他们没参与过任何讨论，也不知道这东西是怎么做出来的，带着自己的问题来读：这个工具能不能解决我的事、下一步该怎么操作、某句说法可不可信。还有一类读者是 **agent**——它没有上下文，只照写着的做，一句歧义就是一步跑偏。
- **目的**：读完能做出三个判断——**用不用**（它解决什么问题、要付出什么）、**怎么用**（照着步骤第一次就能跑通）、**信到哪**（哪些行为由工具保证、哪些要自己把握）。文字帮不上这三个判断，就是公开面失职。
- **口吻**：平静、自信，用用户收益说话——直接陈述能力和边界，不堆修饰；不向读者宣讲内部的设计思路，不记录工作过程，不交代出过的岔子。**每句话都要和读者即将装到的那个版本的行为对得上**：还没发布的不写，已经改掉的不写，改过来的过程更不写。

## 公开面体系：五条通道

文字离开团队，靠的是一个个具体的公开场所——把场所数清，公开面就数清了。按读者遇到它们的顺序排：

### 一、注册表与仓库首页

- npm/PyPI 等注册表的包页：包名、一句话描述（description 字段）、关键词、主页链接；
- GitHub 仓库的 About 与仓描述。

内容全部来自 `package.json`/`pyproject.toml` 与仓库设置。这是读者的第一眼，也是最容易漏掉的一块公开面——**改这些字段的人，就是在发布新广告**。

### 二、公开文档站

- 手写页面（入门/概念/手册等）；
- 图片里嵌的字（站内对比图的 SVG 文字——图上的字读者照样读到，扫 markdown 扫不到它）；
- API 参考页：由源码注释自动生成——**注释即页面**，红线要在写注释那一刻守。

### 三、公开仓库

按两种面目分管：

- **产品面文件**（README/CHANGELOG/模板/demos——用户真会读的）守本宪章全部红线；
- **协作面文件**（CONTRIBUTING/AGENTS.md/CI 配置——写给维护者的工程件）不守宣传红线，但仍只写职责与约束、不留决策史；
- **提交历史与 PR 标题**随 clone 公开且历史不可抹——写提交信息时就要守（平静事实语气，禁内部编号、裁定史、作废词），事后无救。

### 四、安装包内文件

**红线钉在哪**：`package.json` 的 `files` 字段（或等价的白名单）就是随包公开的名单。**往里加一个文件＝多发布一份公开文本**；名单外的文件即使躺在仓库里，也不进这一层。

| 类别 | 内容 | 算不算公开文本 |
|---|---|---|
| 给人读的 | README、LICENSE、包描述 | **算**，全部红线适用 |
| 代码 | `dist/*.js`、`*.js.map` | 不算；map 通常不含源码原文 |
| 类型声明 | `*.d.ts` | **算**——见下 |
| 不在包里的 | CHANGELOG、本地构建产物 | 不进这一层（发布走 CI 干净构建） |

**两个容易漏掉的点**：

1. **类型声明带着源码注释。**`/** 扫描黑名单：发布物文本不得含指定词…… */` 这类 JSDoc 会随包上路，装到用户机器上、编辑器悬停时可见——注释在这里**第二次公开**（第一次是文档站的 API 页）。改注释就是改公开文本。
2. **判断这层不能看本地目录，只能下载线上包看。**本地命令：`npm pack --dry-run`；线上命令：`curl -s https://registry.npmjs.org/<pkg>/-/<pkg>-<version>.tgz | tar tz`。

### 五、运行时输出

**红线钉在哪**：这一层的文字没有专门的文档作者——**写代码字符串的人、改渲染器的人，就是发布者**。代码合并进公开仓的那一刻，这些字就出现在用户的终端和 agent 的上下文里，中间没有单独的"发布"动作可拦。

| 文本 | 谁读 | 怎么到读者面前 |
|---|---|---|
| CLI 输出与报错文案 | 跑命令的人 | 直接写在源码字符串里，合并后每台用户机器上即刻生效 |
| 生成物（渲染出来的提示词/文档/配置） | agent 或人 | 从源码组装，每次发布整批重新生成，没人逐份校对 |

**红线怎么守——这一层靠不了人眼，只能靠代码**：

1. **读者是 agent，不是人。**它没有上下文、只照文本行动，一句歧义就是一步跑偏；产物每次发布整批重生成，没人逐份校对几十个文件。所以凡是"改渲染器一行＝改写所有产物"的文字，把关必须写成代码里的门。
2. **已有的门**：词表扫描接进了 CI（`.github/workflows/self-check.yml`，每次 push 与 PR 跑 `redline-check.mjs --stat`），产物命中即红。结构校验尚未接进 CI——补上或承认它是债。
3. **还缺的门**：靠发布前人工执行的检查，迟早会漏——要么接进流水线，要么承认它是债。

---

**五条通道的共同原则：红线在源头守，不在成品端追。**成品端追不回来：提交历史抹不掉、下载走的包收不回、机器生成的文字没人逐份读。三类源头各自的"公开那一刻"：

| 源头类型 | 例子 | 公开那一刻 |
|---|---|---|
| 手写的 | 文档站页面、包页描述、提交信息 | push 进公开仓那一刻（中间没有单独的审查步骤） |
| 生成的 | 源码注释（进 API 页与类型声明）、图内文字、生成物 | 上游代码合并那一刻（发布动作没有签字环节） |
| 名单的 | files 字段、发布工作流的文件清单 | 往名单里加一个文件那一刻 |

## 红线（出现即违规，发布前逐条自查）

> 每条三行：一句话说清禁什么，"不许"给会踩中的原句，"改成"给出口。
> 检查手段：第 1–9 条在 `scripts/redline-check.mjs` 里各有一条以上正则兜底（宁误报不漏报，误报行加尾注放行）；第 10、11 条机器查不出来——前者靠逐句对账，后者靠人读语气。

1. **内部档案格式**——把对外文字写成了工作记录。
   不许：`裁定：……｜依据：……｜触发重议条件：……` 这类一条一格；或向读者声明 `本记录只追加、不改写`。
   改成：只给结论。记录本身留在内部。

2. **内部过程史**——读者没参与过这项工作；检查流程、轮次和故事对他没有意义，只显得吵闹。
   不许：`经过三轮审计取证`、`验收门全绿`、`最后靠人工逐页收口`。
   改成：删掉。能力本身值得说时，用结果句："产物在构建期自动校验"。

3. **内部编号与黑话**——只有团队内部认得的代号，和已经废弃不用的旧词。
   不许：`票据 #1234`、`第 3 轮返工`、`P2 里程碑` 这类编号出现在对外句子里；已废弃旧词（例：读者看不懂的 `钩子`，现行用语是 `解析入口`）。
   改成：直接说事物本身，说"解析入口"。

4. **缺陷自曝与修复台账**——修复要公布，但不能摆成问题清单。
   不许：公开页出现 `问题×归因×处置` 表格，或 `我们修过的账` 式章节。
   改成：进 CHANGELOG，一行事实即可（例："fix(cli)：`--dry-run` 不再写入缓存目录"）。
   **边界例**：对照句写**读者此前的做法**＝合法——`此前这些文件要自己写脚本拷进输出目录` 服务"用不用"判断，是功能动机不是病历；**列己方此前的问题清单**（编号、归因、`都改掉了`式收口）＝违规。分界＝句子的宾语是读者的旧处境，还是作者方的旧缺陷。

5. **设计哲学布道**——向用户宣讲内部如何思考质量、拆分、评审。
   不许：`我们先区分两种质量，因为……`（把推导过程端给读者）。
   改成：给结论，且结论的主语是产品："这个工具保证同一份声明每次渲染出同样的结构，于是每一步你都能单独核对。"为什么最多讲一句。

6. **未兑现承诺与路线图泄漏**——没做完的事、排期中的事，一个字不写。
   不许：`v0.3.0 将支持增量渲染`、`记在路线上`、`coming soon`。
   改成：做完了再用现在时写；没做完＝不存在。

7. **内部锚点**——离开非公开仓库就看不懂、也查不到的指路信息。
   不许：commit 号、内部工作目录路径、非公开仓库的名字。
   改成：换成公开链接，或删。

8. **自我贬抑式诚实**——诚实是交代边界在哪，不是交代自己曾经多糟。
   不许：`我们曾经在这里制造过质量问题，全部认账`。
   改成：同一事实的现在写法："当前边界：增量渲染支持到文件粒度，行粒度还未覆盖。"

9. **质量混谈**——把两种质量说成一种。工具只承诺**可机检的那部分**：产物忠实、完整、一致地呈现作者的声明；内容本身写得好不好归写作层，不置评。
   不许：`这个工具保证文档写得专业`。
   改成："这个工具保证文档忠实呈现你的配置和用例。"

10. **无据行为宣称（工具承诺句）**——公开面上"会 X／保证 X"的句子，必须有测试或构建期检查与之对上；对不上就补门或撤句。正例：README 里每条"保证"后面都指向一个能当场复跑的测试文件；读者不必相信，他可以自己验。
    边界：这条只管**工具承诺句**；写给 agent 的流程说明是**技能意图句**，允许一定程度的未达成，不逐句索实证。本条无法机器自查，逐句对账在裁决步做。

11. **推责式划界**——写边界时把责任甩给读者。边界要写（诚实边界是产品特色），但句子的主语该是产品做了什么，不是"这事归你"。第二人称免责句读起来像撇清，读者记下的是被推开，不是信息。
    不许：`至于每一步写得好不好——那是你的评估技术的事`。
    改成：同一分界的中立写法——"这个工具保证每一步的输入输出可追溯；每一步的内容对不对，你第一次有了能单独核对的切面。"分界照说，只是把它说成读者拿到手的东西。（本条与第 10 条同属机器查不出、靠人判。）

## 翻译规则：内部信息怎么变成公开文字

内部的东西要出去，走两步——**先裁弃留，再选成品**。

**第一步：裁弃留。**问：读者拿到这条信息，"用不用／怎么用／信到哪"三个判断里会改变哪一个？都不改变的，不翻译——留在内部，这不是损失，这就是分界。内部裁定、审计过程、排期讨论的绝大多数归宿是这里。

**第二步：选成品。**要出去的，只许落成五种成品之一：

| 成品 | 回答读者的哪个判断 | 落在哪 | 例子 |
|---|---|---|---|
| 特性卡 | 用不用——它给我什么 | 首页、why 页 | "每次运行都留下独立的结果文件，于是同一次任务的各阶段可以分开核对、分开重跑" |
| 操作路径 | 怎么用——下一步做什么 | 快速上手、手册 | 开头给三行的最短路径：装、跑、看输出在哪 |
| 边界声明 | 信到哪——管到哪不管到哪 | 契约页、各页边界框 | "不承诺什么"三条，每条一句、不展开论证 |
| 设计立场 | 为什么——最多一句 | 任意页的按语 | "默认不提供没有真实用例的抽象选项。"（前一句给事实，这一句给立场，到此为止） |
| CHANGELOG 条目 | （只回答"这个版本改了什么"） | CHANGELOG | 唯一允许写"做过什么"的地方，一行事实体："fix(render)：示例标记不再逐行重复，改由区块题注一处承载" |

**一个完整的翻译实例**——内部事实是"渲染器一度在产物里制造质量问题，已修复、且已加了机器门"。

- **错误翻译**：在案例页加一节 `我们修过的账`，把 `问题×归因×处置` 列成表。过程史和 `缺陷台账` 直接端给读者（踩红线 2、4）。修好了也不能这么写——读者要的是这个版本的行为，不是作者方的病历。
- **正确翻译**：同一个事实拆成两处——修复本身进 CHANGELOG 一行（上表第五种）；能力边界进契约页一句现在时："当前边界：产物文本由构建期校验守，覆盖到结构层，措辞层不承诺。"读者拿到的是边界，不是作者方的病历。

## 发布前自查（强制）

**门＝按宪章逐条判过，且换过一次眼睛；脚本只是召回工具。**要发布任何公开面内容（站页／包内文件／公开仓文件／生成物），先过审计；FAIL 不清零不发布。

1. **逐条出判**：口吻与读者三判断（用不用／怎么用／信到哪）、翻译规则第一步（这条信息该不该出去）、红线 1–11 逐条。判据全在本宪章，逐条记四值（证实／驳倒／部分／无定）。
2. **跑一遍脚本作词表召回**（`node scripts/redline-check.mjs <文件>…`）：作废词与内部锚点交给正则保证扫到；每条命中逐条裁决——真违规改写或删除，误报记下理由放行。
3. **换一次眼睛**：收口前交给一个没写过这些字的新上下文 agent，只问它"哪句你不知道谁在做、哪句像在跟自己说话、哪句你会怀疑、哪句你猜作者没意识到"；它给反应不给判据（见 `references/review-brief.md`）。
4. **输出**：PASS／FAIL＋逐条证据（文件:行）。FAIL 处置后复审。

**为什么"换眼睛"不能省，但也不该开很多次**：它补的不是判据覆盖率（那是第 1 步的事），而是**作者看不见自己那句话在陌生人眼里是什么意思**。这件事开十次和开一次没有差别，开一次和不开差别很大。实测一轮 45 条裁决：25 条靠读文本判，而这些不需要陌生视角；真正只有陌生视角能抓到的，是"我写的时候知道自己在说什么，读者不知道"那一类。

**为什么脚本不当门**：脚本只查得到词面——语气、弃留、红线 10 和 11 它都看不见。词表规则必然误报（示例数据、评分数字、模板占位符都会撞上），逐条裁决离不开会思考的读者。但它的价值是稳定——内部路径、编号残留、作废词这类硬伤交给正则，比任何人的记性可靠。**脚本清零 ≠ 可发布，PASS 才是。**

**本仓库自己也跑这一套**：`.github/workflows/self-check.yml` 在每次 push 上跑词表脚本（自己扫自己），`examples/walkthrough/` 记录一次完整的四步审计。程序先过自己的门。
