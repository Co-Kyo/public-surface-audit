# 图基座：本 skill 建立在 graphify skill 之上

> **本 skill 是强制依赖 graphify skill 的**：没有 graphify 技能与 graphify 命令，本 skill 不运行、不降级、不给"手工版"。
> 判断仍是人的；但**检索、配对、记忆一律走图**。这份文件说明图在审计里承担什么、放在哪、怎么维护。

## 「命令在、但没有 LLM key」怎么算

这是唯一一个 skill 必须自己定义的状态，不能留给执行者临场发挥。分三档，都不是"降级退出"：

| 状态 | 表现 | 怎么办 |
|---|---|---|
| 有 key | `graphify extract .` 成功，文档有语义节点 | 正常流程 |
| **无 key** | `graphify extract .` 报 `no LLM API key found` | **改用 `graphify update`**——它免 key，产出代码符号 + 文档的 page/heading 结构节点。图可用，只是文档节点是结构而非语义 |
| 无 key 且 `update` 也不可用 | 命令本身跑不起来 | 这才算没有基座：停下并报告作者，不要开审 |

判据是**图里有没有节点**，不是"有没有 key"。`status` 会打印文档节点数；为 0 且代码节点 > 0 时显式警告"图只覆盖代码符号"，此时配对只对代码类声称有效。

无 key 的代价是**文档语义配对变弱**（`query` 找不到"这句话在讲哪个行为"），但文档的标题结构与代码符号都还在——这已经够跑队列。**不要在无 key 时退回 `--code-only`**：那个图的文档节点是 0，配对能力实际已失效，却和正常图长得一样，最容易被误当成"干净"。

## 为什么是地基而不是配件

审计的本质是**跨载体一致性**：文档说 X，实现是 Y。这句话展开就是一堆"声称 ↔ 实现"的多对多关系，还要跨轮次记住"哪些核过、改没改"。这正是图的形状：

- **节点**：声称（claim）、实现符号、文件；
- **边**：claim→符号 的"约定"关系（配对即图查询）；
- **裁决**：claim 节点上的属性（`audit_verdict`／`audit_note`／`audit_file_hash`）——**记忆就是图本身**；
- **增量**：文件内容哈希没变的声称不再入队——审计跟着内容走，不跟着时间走。

手工审计做不到最后一条，因为它没有持久的共同记忆；这也是"重复审计"的根治办法。

## 审计工作区：住在被审仓里（对象视角）

审计记忆属于**被审对象**：谁的公开面被审，工作区就放谁的根目录。

```
<被审仓>/
  .audit/                        ← graph-audit init 创建；自动写进 .gitignore
    graphify-out/graph.json      ← 图基座（graphify 技能生成与更新）
    claims.json                  ← 声称层账本（写前记录，读取走图）
    verdicts.json                ← 裁决层账本（写前记录，读取走图）
    rounds/<日期-slug>/          ← 每轮的证据单、裁决表、复查与收口记录
  .gitignore                     ← init 自动加入 .audit/（不存在则创建）
```

一条 `.gitignore` 记录解决三件事：不进版本库、不进公开面（git 视角）、graphify 的 gitignore 感知扫描通常也不会把它卷进图。init 之后仍要核对一次 detect 清单：**`.audit/` 下的文件不得出现在被审文件集里**——它是审计工具自己的影子，不是被审面。

> 这条约定取代了早期"图必须建在被审目录外面"的做法。旧做法能防污染，但审计记忆无家可归、跨轮丢失；新做法把记忆还给对象仓，靠 gitignore 与文件集排除防污染——**两全，但排除必须每轮核一次**。

## 三层结构（深结合）

| 层 | 是什么 | 在哪 | 谁写 |
|---|---|---|---|
| 图基座 | graphify 知识图：文件、符号、社区 | `.audit/graphify-out/graph.json` | graphify 技能（build／update） |
| 声称层 | claim 节点 ＋ claim→符号 配对边 | 同一张图（`_origin: "audit-overlay"`） | `graph-audit ingest-claims` |
| 裁决层 | claim 节点上的 `audit_*` 属性 | 同一张图 | `graph-audit record` |

**读取一律走图**：排队看 claim 节点与配对边，跳过判断看 `audit_verdict` 与 `audit_file_hash`。两个账本（claims.json／verdicts.json）是写前记录——`graph-audit reconcile` 用它们把审计层贴回图。

> 关于"update 会不会冲掉审计层"：**实测不会**。`update` 与 `extract --force` 都会保留 `_origin: audit-overlay` 的节点及其边；只有**源文件被删除**时，挂在该文件上的 claim 节点才会被连带驱逐（节点没有落点了）。所以 `reconcile` 不是"每轮必跑的补救"，而是"贴回确认"——跑它是为了在源文件增删之后把记忆补回来。

## 标准流程（四步的图化形态）

```bash
# 0 · 初始化（每仓一次）——打印建图命令并写 .gitignore
node scripts/graph-audit.mjs init --root <被审仓>

# 1 · 建图（首轮）／增量（以后每轮）——同一条命令
cd <被审仓>
export GRAPHIFY_OUT=<被审仓>/.audit/graphify-out   # 必须！否则图写到仓根，本脚本不读
graphify update

# 2 · 抽声称（先只读文本、此时不打开实现，按 references/claim-extraction-spec.md）
#      产出 claims.json —— 它的写入时间早于任何核量记录，这就是顺序凭据

# 3 · 声称入图 → 排队
node scripts/graph-audit.mjs ingest-claims --root <被审仓> --in claims.json
node scripts/graph-audit.mjs queue --root <被审仓>

# 4 · 逐条核 → 记裁决
node scripts/graph-audit.mjs record --root <被审仓> --item <id> --verdict <证实|驳倒|部分|无定> [--note ...]

# 5 · 汇总
node scripts/graph-audit.mjs status --root <被审仓>
```

### 图在四步程序里各管什么

| 步 | 图怎么用 | 产物 |
|---|---|---|
| 00 定标 | 节点去重＝文件全集（五通道归类）；社区分组切批次；**孤岛节点＝最容易漏的公开面** | `.audit/rounds/<轮>/00-scope.md` |
| 01 取证 | 第一段只读文本（**不碰图**）→ 写 claims.json；第二段 ingest-claims 入图 → queue 排队（符号定位实现、量对照） | 每批 `01-evidence-B{n}.md` |
| 02 裁决 | 逐条核量 → record 记四值 → 图上裁决属性 | `02-verdict.md` ＋ 图上裁决属性 |
| 03 收口 | status 汇总四值；判定计数与批次 FAIL 对齐；**图不进对抗复查的输入**（见下方界线） | `03-review.md`／`03-close.md` |

**第一段不许看图，这是硬约束。**图里已经有实现结构，先看图再抽声称，抽出来的就不是"读者会怎么理解这句话"，而是"我知道实现是这样，所以这句话在说 X"。顺序凭据（`claims.json` 写入时间早于首次 `queue`）就是为了让这件事可查。

## 查图：图的用处不在建，在查

只建图不查图，等于买了个索引却不翻。下面这些命令在配对和定位上直接省掉整轮翻源码，**都用同一个 `GRAPHIFY_OUT`**：

| 命令 | 什么时候用 | 实测收益 |
|---|---|---|
| `graphify explain <符号>` | 要某符号的完整调用链（带行号、含上下游） | 一条命令给出 `L145 → L156 → L179`，不必读整个文件 |
| `graphify query "<词>" --budget 600` | 抽声称时先缩范围：文档提到某个行为，先看它在哪些符号附近 | 命中几个符号再精读命中段，比通读便宜一到两个数量级 |
| `graphify affected <符号>` | 改实现前要知道会波及谁 | 判"某句承诺还成不成立"时先看影响面 |
| `graphify god-nodes` | 定标时找架构枢纽 | 枢纽附近的公开面描述最容易糊（大家都以为它显然） |

**`--budget` 要小，且要实测。** 在 373 节点 / 352 边的真图上扫过一轮（`query "redline"`）：

| 预算 | 输出字符 |
|---|---|
| 200 | 1,212 |
| 400 | 1,793 |
| 600 | 2,330 |
| 700 | 2,679 |
| **750** | **5,696 ← 突然翻倍** |
| 默认 / 2000+ | 5,351 |

预算过了一个阈值就失效（输出比默认还大），所以**不要照抄一个数就走**——先用小预算跑一次，看输出量涨没涨。`--depth` 实测无效（与默认一致），别指望它。

`explain` 与 `affected` 是符号级的，文档类声称（"保证可读""设计得体面"）它们永远命中不了——那部分靠人读，见文末。

## 一条不许越的界：图不进"换眼睛"那一步

裁决在主会话里做，图当然给主会话。唯一不许拿到图的是**收口前的对抗复查**：

| 谁 | 拿到什么 | 绝不能拿到什么 |
|---|---|---|
| 主会话（取证与裁决） | 全部：图、queue、记忆账 | —— |
| 对抗复查 agent | **只有宪章和拟发布文本** | claim 节点、源码、裁决表、术语表、其他批次 |

理由不变：它的全部价值在于它不知道实现是什么样。给了它 queue 或裁决表，它就会替你的结论说话——而它本该提供的是"我什么都不懂时读到了什么"。见 `references/review-brief.md` 的"不要做的事"。

## 队列的评分与含义

`queue` 把"声称的量"与"实现里的量"并列，按可疑度排序：

| 分 | 含义 |
|---|---|
| 10 | targets 里的符号**图与源码都找不到**（最可疑：文档描述了不存在的东西） |
| 9 | 声称只提某个退出码，实现里还有别的退出码（**方向对、细节错**） |
| 8 | 声称的量在函数体内没出现 |
| 7 | 部分 targets 找不到 |
| 1–6 | 量都对上了，仍需人确认 |

`future`／`process`／`quality`／`reference` 四类不进配对——抽出来即违规候选（红线 6／2／9／7），**这是最大的效率来源：大部分违规根本不用核代码**。

### 行数的口径（量核对里最容易误报的一处）

同一个文件能数出两个行数，差在末尾有没有换行：

```bash
printf '.a{}\n.b{}\n.c{}' > three.css
wc -l three.css               # 2   ← 数换行符
awk 'END{print NR}' three.css  # 3   ← 数内容行
```

**写文档的人几乎都用前一个**（`wc -l`、`git diff --stat`）。所以 `queue` 以 `wc -l` 为准，同时把两个口径都报出来：

```
实测 2 行（wc -l）／3 行（含末尾无换行）
```

**命中任一即算对上**，两个都对不上才判"量未出现"。末尾有换行的文件两个数相同，输出里就只报一个数。

**目录聚合按全部文件算。** `targets` 写一个目录（如 `css/`）时，实测报目录内所有文件的行数与字节数之和，与 `cat css/*.css | wc -l` 一致。这类"整站 1450 行"的声称因此可核——**但只在这个仓的目录划分恰好等于声称口径时成立**；跨多个目录的聚合（`css/` + `tokens/`）仍核不到，须人读，别把它当成核过了。

**队列为空不等于没有无据宣称**："我们保证写得专业"这种句子在代码里没有对应物，抽不出 targets，靠人读。图管的是可核验的那部分，判断仍是人的。

## 实测陷阱（每条都真踩过）

1. **`.audit/` 卷进被审文件集**：建图后必须核一次 detect 清单。`redline-check.mjs` 已跳过 `node_modules`、`.git`、`.audit`、`graphify-out`——但**别的扫描工具未必**，换工具时先确认它排不排 `.audit/`。
2. **`graphify update` 会把图写到仓根**（最容易踩）。`update` 写的是「目标目录上一级的 `graphify-out/`」，**不接受 `--out`**（`error: unknown update option: --out`）。按 `cd .audit && graphify update` 跑，图就落在仓根，而脚本读 `.audit/graphify-out/`——两条路各写各的图，**增量永远不生效，队列一直读旧图**。正确做法是设 `GRAPHIFY_OUT=<被审仓>/.audit/graphify-out`（绝对路径，与当前目录无关）。`status` 与 `queue` 检测到仓根另有一张图会显式报警。
3. **首建不必用 `extract`**：无 LLM key 时 `graphify extract .` 直接失败，`--code-only` 又只给代码节点（文档 0 个）。**`graphify update` 从零跑就能建图**，且免 key 产出文档的 page/heading 结构节点。文档节点靠它，语义节点才需要 key。
4. **`--force` 只在需要时用**：图提示「pre-#1504 node-ID scheme」时跑 `extract --force` 换全路径 ID，避免同名文件撞车。日常增量不需要。
5. **词频配对不可用**（已被符号配对取代，留档）：靠"共同的词"配对在真语料上排出 3 条**全部误报**——`check`、`push` 这类词到处都是。配对靠符号，不靠词。
6. **裁决不带文件哈希**：record 时文件不可读就没记到哈希，该条永远会重新入队——提示信息会明说，别忽略。

## 图的硬边界：CSS 与无扩展名文件进不来

`graphify` 只对认得的扩展名抽节点。实测一个含 `base.css` 的仓：

```
[graphify extract] 1 file(s) not classified (no supported extension or shebang), skipped: base.css
```

样式文件里的注释往往正是公开面（"卡片圆角 8px"这类承诺就写在注释里），**它们永远进不了图**。这不是配置问题，是支持范围问题。

处置：**注释体文件（CSS/SCSS/Less）的公开面由人直接读，不要指望图能覆盖**。抽声称时把这类文件单列一批，`00-scope.md` 里写明"本批无图可依"。同理，图里 0 个文档节点时 `queue` 的配对能力只对代码符号有效——脚本会在 `status` 与 `queue` 顶部显式警告，不要看着"队列为空"就判"没有无据宣称"。

## 图替代不了的三件事

1. **判断**：量对不上也可能是你读错（同名函数、分支差异），必须逐条打开原文确认。图给的是"哪段文字关于这个主题"，不是"这句话违不违规"——拿 `query` 问一个语气问题，它会返回几十个相关节点，一个都不回答你。
2. **作者看不见自己那句在陌生人眼里什么意思**：这是唯一必须换一双眼睛的事，也是对抗复查存在的全部理由。图在这里帮不上，因为它知道得太多。
3. **没有具体量的句子**：质量自评、愿景、口吻问题，靠人读——但这些恰好是 `future`／`process`／`quality` 类声称能直接抓住的。
